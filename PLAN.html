Sedaia Designs Monorepo Plan

A safe, history-preserving migration for the Sedaia Designs platform and Sakura Sedaia portfolio, with independent builds and deployments across Vercel and Google Cloud Run.

Recommended decision

Import the portfolio history into the root repository. Place it at apps/portfolio, remove its nested .git only after the import is verified, and retain the original GitLab repository as a protected deployment fallback.

Rename the three current modules according to responsibility:

  • webapi → apps/api
  • web-central → apps/business-site
  • web-portfolio → apps/portfolio

Gradle should own Kotlin/JVM work from the root; pnpm should own frontend applications and TypeScript packages from the root. Neither build system should wrap the other.

Principal migration risks

  1. Uncommitted portfolio work: removing or relocating its .git now could detach working changes from their history.
  2. Vercel Git integration: preserving vercel.json alone does not preserve the connected repository, project root, domains, or environment variables.
  3. Nested repository behavior: initializing root Git while the nested .git remains can stage the portfolio as an embedded repository/gitlink rather than normal files.
  4. History loss: deleting the nested .git and adding the snapshot would lose usable portfolio ancestry.
  5. Dependency drift: replacing two lockfiles with a root lockfile can change resolved versions, particularly because the applications currently use different SolidJS RC versions.
  6. Path-sensitive deployment: moving the portfolio changes Vercel’s configured root directory and install context.
  7. API readiness: the API lacks /v1/portfolio, OpenAPI, CORS, a container definition, Cloud Run port handling, and stateless persistence.
Do not perform repository surgery before a verified backup. Root Git initialization, nested .git removal, history rewriting, module moves, and Vercel changes remain outside the approved scope until this plan is reviewed.

Migration phases

1

Establish a recoverable baseline

  • Resolve whether each modified and untracked portfolio file should be committed or archived.
  • Push the chosen clean portfolio state to GitLab.
  • Create and verify a git bundle --all backup.
  • Create a filesystem archive that includes ignored local state.
  • Record Vercel project identity, domains, environment variables, Git connection, build settings, and the known-good production deployment.
2

Import portfolio history

Build the root repository in a staging location or temporarily preserve the current portfolio directory so the destination path is empty. Import its history under apps/portfolio.

Preferred options:

  • Filtered-history merge: transform a temporary clone with git filter-repo --to-subdirectory-filter apps/portfolio, then merge it. This produces clean path-aware history.
  • Git subtree: import with git subtree add --prefix=apps/portfolio. This is simpler and preserves ancestry without rewriting the source repository.

Never rewrite the original GitLab repository.

3

Verify, then remove the nested repository

  • Compare the imported tree with the preserved working copy.
  • Verify history with git log --follow -- apps/portfolio/….
  • Confirm the bundle and GitLab repository can restore the source.
  • Only then remove the nested web-portfolio/.git.

A permanent submodule is not recommended because it would preserve separate source-control ownership and complicate shared-package changes.

4

Establish root ownership and ignore rules

Add root rules for dependency directories, build output, local databases, IDE state, system metadata, Vercel local metadata, and local environment files. Continue tracking source files, lockfiles, the Gradle wrapper, application deployment configuration, and intentional contract artifacts.

5

Centralize Gradle

  • Move the wrapper, settings, repositories, and version catalog to the root.
  • Include apps/api as the API subproject.
  • Retain Java 21 through toolchains.
  • Support scoped commands such as ./gradlew :apps:api:test and ./gradlew :apps:api:build.
6

Centralize pnpm

  • Create a root workspace for apps/business-site, apps/portfolio, and packages/*.
  • Pin Node 22.18 and pnpm 10.22 in root metadata.
  • Preserve each frontend’s scripts and standalone build behavior.
  • Replace the application lockfiles with one root lockfile in a dedicated, reviewable change.
  • Review dependency changes instead of silently normalizing SolidJS versions during the move.
7

Introduce the API contract

  • Make OpenAPI the source of truth for public operations and data shapes.
  • Add the canonical https://api.sedaia-designs.org/v1/portfolio operation.
  • Generate or validate packages/api-client in CI.
  • Make schema/client drift fail validation.
8

Add root documentation and CI

Document ownership, versions, local development, environment variables, scoped commands, deployments, and rollback. Use path-filtered jobs for the API, business site, portfolio, and contract client so unrelated applications remain independent.

Portfolio deployment transition

  1. Leave the production Vercel project connected to GitLab while the monorepo version is validated.
  2. Build the portfolio from the root workspace and compare its output with the known-good deployment.
  3. Use a temporary preview project or controlled preview deployment.
  4. Configure the root directory as apps/portfolio while retaining the same build and output behavior.
  5. Preserve the existing project, environment variables, and production domains.
  6. Switch the Git connection only after preview parity is established.

Cloud Run corrections required

  • Listen on 0.0.0.0 and read PORT, defaulting locally to 8080.
  • Replace file-backed H2 for deployed persistence.
  • Do not run database migrations implicitly on every instance startup.
  • Add explicit liveness/readiness routes, CORS, structured logs, graceful shutdown, and scaling constraints.
  • Return safe error responses rather than exception text.

Rollback strategy

Before history import

Keep a verified Git bundle, filesystem archive, and pushed GitLab state.

Before Vercel switch

Record the project configuration and verify a monorepo preview against production.

After Vercel switch

Retain the original GitLab repository and known-good commit for a defined rollback window.

Rollback action

Reconnect the existing Vercel project to GitLab and restore its prior root/build settings. Keep the same Vercel project so domains do not need transfer.

Acceptance criteria

  • A fresh checkout installs and validates the Gradle and pnpm workspaces using documented commands.
  • The portfolio history is accessible within the root repository.
  • The original GitLab repository and backup bundle can restore the pre-migration state.
  • Every application builds independently without building unrelated applications.
  • The portfolio’s preview output and behavior match the current production site.
  • The existing Vercel portfolio project, domains, and environment variables remain intact.
  • The API runs on a configurable port and its container starts locally.
  • Liveness, readiness, and /v1/portfolio are testable.
  • OpenAPI/client drift fails CI.
  • No secret or machine-specific IDE state is required to build the repository.
  • A failure or deployment in one application does not require deployment of another.

Approval gates

The following actions should be reviewed and explicitly approved before execution:

  • Final naming and target directory layout.
  • Choice between filtered-history merge and subtree import.
  • Root Git initialization and initial ignore rules.
  • Removal of web-portfolio/.git.
  • Movement of the three existing modules.
  • Consolidation of frontend lockfiles.
  • Any change to the existing Vercel project or Git connection.
  • Any deletion, archival, or rewrite of the original GitLab repository.
